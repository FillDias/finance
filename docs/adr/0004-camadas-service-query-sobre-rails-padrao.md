# Camadas services/queries em vez do padrão Rails "fat model"

Projeto solo, sem necessidade de arquitetura hexagonal/clean architecture completa, mas com risco real de lógica de negócio (geração de parcelas, projeção de fatura, status de obrigação) se espalhar entre models e controllers se seguirmos o padrão Rails puro. Decidimos separar em quatro camadas: `app/models` (ActiveRecord puro — validações, associações, scopes de tabela única, sem cálculo de negócio); `app/services` (um objeto PORO por caso de uso de escrita, ex. `CriarCompraNoCartao`, `GerarParcelas`, `QuitarSaldoHerdado`, nomeados em português seguindo o `CONTEXT.md`); `app/queries` (um objeto PORO por leitura agregada, ex. projeção de Fatura, Saldo restante, Utilização do limite, KPIs e próximos vencimentos do Painel); `app/controllers` (só orquestra: chama o service/query certo e renderiza).

Services e queries compartilham uma convenção única de chamada via módulos base: `ApplicationService`/`ApplicationQuery` (nomes de infraestrutura em inglês, como `ApplicationRecord`), fornecendo `.call(params)` e retornando um `Resultado` (`sucesso?`, `valor`, `erros`) no caso dos services. Isso evita que cada service reinvente seu próprio formato de retorno.

Queries são a fonte única da verdade para qualquer valor derivado (Fatura projetada, Saldo restante, Utilização do limite, status de Obrigação). Quando um service de escrita precisa desse valor para validar algo (ex.: `CriarCompraNoCartao` checando limite disponível antes de aceitar a compra), ele chama a query correspondente em vez de recalcular — evita duplicar a mesma conta entre o caminho de leitura (Painel) e o de escrita (validações).

Alternativa rejeitada: manter o padrão Rails padrão de model gordo (validações + lógica de negócio + scopes de agregação no mesmo lugar), que tende a acumular método demais no `Cartao`/`Compra` conforme o projeto cresce, e mistura lógica de leitura (dashboard) com lógica de escrita (regras de criação) na mesma classe. Também rejeitamos uma arquitetura hexagonal/clean completa (camadas de ports/adapters, casos de uso desacoplados de ActiveRecord) por ser complexidade desnecessária para um projeto solo.
